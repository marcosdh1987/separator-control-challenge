# Internationalisation

> **Language**: English (canonical technical reference).

The simulator ships in English and Spanish. Spanish is not an afterthought: the
audience includes Spanish-speaking field operators, and the teaching material is
written for them.

## Why no i18n library

The application is a static, client-heavy simulator with no backend. It does not
need locale routing (`/es/...`), server-side negotiation, or message formatting in
server components — the three things a library like `next-intl` mainly provides.
What it does need is a typed dictionary and a hook, which is about a hundred lines.

Two further reasons decided it:

- **Messages that need grammar are functions, not templates.** The score explanation
  used to be built by concatenating fragments (`` `${loopName} tracking error…` ``),
  which forces every language into English word order. Each such message is now a
  typed function per locale, free to inflect and reorder. An ICU string could not
  give the same compile-time guarantee that a message receives the arguments it
  expects.
- **No new runtime dependency.** The app makes no network calls and uses no AI at
  runtime; keeping the dependency surface small is a project-wide constraint.

## Layout

```
lib/i18n/
  locale.ts        Locale type, browser detection, storage
  store.ts         The locale as an external store (see "Hydration")
  provider.tsx     LocaleProvider, useMessages(), useLocale()
  test-utils.tsx   renderWithLocale() for component tests
  messages/
    index.ts       Composes namespaces; defines Messages
    en/*.ts        Canonical copy (research.ts holds the Research Lab copy)
    es/*.ts        Spanish, typed against its English counterpart
```

English is canonical: `Messages` is `typeof en`, and each Spanish namespace is
declared as its English type. **A missing or misspelled key is a compile error**,
not a blank space at runtime, so `npm run typecheck` is the parity check.

Namespaces are split by screen (`common`, `landing`, `challenge`, `onboarding`,
`education`, `simulation`) so unrelated work touches unrelated files.

## The engine has no language

`lib/simulation/` reports **structured codes**, never prose:

| Instead of | The engine returns |
|---|---|
| `safety.label: "Total level high alarm"` | `safety.condition: "total-high"` |
| `score.diagnosis`, `score.suggestion` | `score.feedback: FeedbackCode` |
| `modifier.label` | `modifier.id` (plus `trip` for the trip modifier) |
| `score.rank: "Process Engineer"` | `score.rank: "engineer"` |
| `scenario.name`, `scenario.description` | the interface resolves them from `scenario.id` |
| `disturbance: "Feed step active"` | `disturbance: "feed-step-active"` |

`FeedbackCode` carries only what the wording needs — which loop, which valve, which
kind of loss — so a translation composes its own sentence. `feedbackCopy()` in
`lib/i18n/messages/en/simulation.ts` turns a code into the reader's language.

The same rule applies to teaching material: `lib/education/diagnosis.ts` owns the
`DiagnosisPatternId` vocabulary, and `lib/education/pid-content.ts` keeps only
identifiers, presentation order, and bibliographic facts. Citations are quoted as
published and never translated; only each reference's `description` is localised.

## Hydration

Pages are prerendered as static HTML in the default locale, so the visitor's real
preference can only be applied on the client. The locale is exposed through
`useSyncExternalStore`: React renders the server snapshot (always English) during
hydration, then immediately re-renders with the detected locale. This is why the
locale is not read with `useState` plus an effect — that would either mismatch the
server markup or trigger a cascading render.

Detection order: an explicit stored choice wins over the browser preference, so a
Spanish speaker who switches to English stays in English. Only the primary subtag
matters — `es-AR`, `es-419` and `es` are all Spanish.

## Tests

Component tests render through `renderWithLocale()`, which pins a locale and turns
detection off. They assert **English** wording by default, so editing a translation
cannot break an unrelated suite. Tests that are about the translation itself pass
`{ locale: "es" }` explicitly.

Where a test asserted engine prose, it now asserts the structured code *and* the
English rendering of it, so both a wrong attribution and a wrong sentence are caught.

## Adding a string

1. Add the key to the right namespace in `lib/i18n/messages/en/`.
2. Run `npm run typecheck`; it will fail until the Spanish file has the key too.
3. Read it in a component with `useMessages()`.

Text that varies by grammar (anything you would otherwise build with `+` or a
template literal containing another translated word) belongs in a function, not a
concatenation at the call site.

Two constraints worth remembering:

- **Spanish runs 20–25% longer than English.** Check layouts with fixed `ch` widths
  and uppercase, letter-spaced labels.
- **The 3D scene mounts its own React reconciler**, so context does not cross the
  `<Canvas>` boundary. Resolve strings in `SeparatorScene` and pass them down as
  props; calling `useMessages()` inside a scene component throws.

## Documentation language policy

Adopted from the DACS project: explanatory and onboarding guides may be written in
Spanish for clarity; canonical technical and scientific references stay in English,
for consistency with the code and so they can be cited. Every document declares its
language in a header line, as this one does. Where the two disagree, the canonical
English document wins.
